## 2. Operating rules
1. **Work phase by phase** following §16 *Implementation Roadmap* (P0 → P9). For each phase: implement → verify → test → write a phase report → only then start the next phase. Do not skip ahead; do not merge phases.
2. **Verify against official documentation and sources**, not memory. Close every `V-nn` item that the current phase lists (and any you touch) by running the command or reading the primary source; record result, command output/link and date in `DECISIONS.md`. Never invent package names, UCI options, ubus methods, nft/dnsmasq/OpenVPN syntax, or file paths. If you cannot verify something, say so, mark it `UNVERIFIED` in code comments + `DECISIONS.md`, and choose the safest fallback.
3. **Build and test for real where possible**: build with the OpenWrt SDK for `ipq40xx/chromium` (§14.1), run lint and unit tests, and run the integration harness (§15.2: netns topology on an OpenWrt x86/64 25.12 rootfs container or QEMU). If your environment lacks network, Docker/QEMU, or the SDK, **state exactly what could not be run**; do not fabricate output, logs, benchmark numbers or "tested on device" claims.
4. **Be honest about hardware.** Nothing may be reported as verified on the Google WiFi AC-1304 unless you actually ran it there. Provide `tests/device/` scripts and a checklist so a human can run them, and list them as "not executed" in the final report.
5. **Ambiguity or contradiction protocol.** If the plan is ambiguous, incomplete, or a verified fact contradicts it: **stop that task**, state the conflict precisely (plan section vs. evidence), propose a fix with trade-offs, record it in `DECISIONS.md` (`ID, date, context, options, decision, impact on PLAN sections, status`), apply the proposed fix only if it does not change owner-visible behaviour beyond the recommended defaults in §19; otherwise ask me. Never silently deviate.
6. **Scope discipline.** Honor Non-Goals (§1.3). Every added component must be justified in `DECISIONS.md` (the plan prefers the simplest robust architecture). No compiled code (C-01). Dependencies only from official OpenWrt feeds (C-02).

## 3. Quality rules (non-negotiable)
- **No hardcoded secrets**, keys, tokens, real hostnames or personal data. Private signing keys never enter the repo (CI secrets only). Test keys are generated by test scripts.
- **Input sanitization everywhere** (§10.2, §12): whitelist validators in one library; ucode `system()`/exec with **argv arrays only**; no `eval`; no string-built shell commands from user data; ids/roles/categories validated and paths canonicalized and confined; strict size/line/count caps; no secrets in logs/rpc/UI.
- **`shellcheck` clean** (`-s sh`), `ucode -c` clean on every `.uc`, ESLint clean on LuCI JS, valid JSON for menu/ACL, `.po/.pot` consistent.
- **Idempotent scripts**: running start/stop/reload/apply/uninstall twice must be safe; repeated `uci-defaults` must not duplicate sections.
- **Safe failure** (G4, FR-27): a failed start/apply rolls back every nft/ip/dnsmasq/firewall change via the undo journal; the router must never be left without internet (unless the user enabled the kill switch) and **never lose LAN/SSH/LuCI access**; `panic` must always work. Test these explicitly (AT-19).
- **No destructive changes to the user's network config without backup** (back up `/etc/config/firewall` once before the first edit; never edit `/etc/config/dhcp` or `/etc/config/network`; remove only what you created — named `geovpn_*` sections).
- **Do not leave stubs**: no `TODO`/`FIXME`/placeholder implementations in delivered code, except explicitly listed `UNVERIFIED` items with fallback behavior.
- Keep the footprint targets (NFR-01…04) and measure when possible; replace budget numbers in §13 with measured ones only if you really measured them.
- Follow OpenWrt conventions (file modes per §8.5, `conffiles`, `keep.d`, `uci-defaults`, procd `START/STOP`), and LuCI conventions (`luci.mk`, menu.d/acl.d, `rpc.declare`, `_()` strings, DOM helpers; no `innerHTML` with data).
