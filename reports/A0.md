## 6. Architecture & Risk Synthesis (Answers to Prompt §10)

### (a) Understanding of the Architecture
GeoVPN's architecture centers on the principle that the core split-tunneling engine (the `inet geovpn` nftables table, fwmark bits `0x0f000000`, policy routing table 4200, rule priority 700, and dnsmasq domain routing) is **completely protocol-blind**. Every VPN protocol (OpenVPN, WireGuard, IKEv2) is abstracted as an interchangeable **driver** exposing a uniform lifecycle interface (`start`, `stop`, `facts`) that operates on a context object (`ctx = {kind, dev, table, mark, rundir}`). Under normal operation (`kind: active`), the driver binds to the fixed network interface `geovpn0` and installs default routes into routing table 4200. Under testing (`kind: test`), the **same driver logic** brings up an isolated secondary virtual device `gvt0` bound to routing table 4300 and fwmark `0x03000000` (TEST mark). The test path is **fail-closed** by design: routing table 4300 installs an unreachable default route (`ip route replace unreachable default table 4300`) *before* any test tunnel is raised, and packets destined for the test endpoint are explicitly marked via concatenated `(ip . port)` nft sets with a 90-second timeout. Because `gvt0` is isolated from the fw4 zone `geovpn` and table 4200 is untouched, test traffic can never leak into the active VPN tunnel, the WAN interface, or interfere with active client traffic.

### (b) The Three Most Dangerous Risks
1. **Accidental Traffic Leakage During Isolated Tests (RA-04 / C-07)**: If destination set marking captures unrelated router traffic or if a test tunnel collapses mid-test, test packets could leak over unencrypted WAN. Mitigation: Table 4300 is initialized with `unreachable default` before link creation, nft marking strictly uses ephemeral `(ip . port)` tuples with 90 s expiry, and all operations are recorded in an undo journal prior to execution.
2. **strongSwan / IKEv2 State Coexistence & Package Volatility (RA-01, RA-03)**: strongSwan previously disappeared from OpenWrt 25.12 feeds, and managing `charon` risks unloading user SAs or disrupting local IPsec configurations. Mitigation: strongSwan is isolated into the optional `geovpn-ikev2` package; we employ XFRM interfaces with dedicated `if_id`s, manage only `gv_*` connections via `swanctl`, never kill or restart a foreign `charon`, and provide an empirical probe-only fallback if connection isolation is unsafe.
3. **Flapping and Premature Failover Under Marginal Link Conditions (RA-07)**: Poorly configured health checks could cause rapid ping-pong switching between tunnels, repeatedly tearing down connections and causing packet loss. Mitigation: Hysteresis logic, test-before-switch verification, exponential backoff, a minimum switch interval (60 s), and an hourly rate limit (maximum 6 switches/hour).
